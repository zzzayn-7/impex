# Deploying Impex on AWS (Terraform + SSM)

```
Internet ──► Elastic IP ──► EC2 (Amazon Linux 2023, t3.small)
                              └─ Docker Compose = the same stack as local development, plus the EDGE:
                                 edge (Caddy)  443 -> Super Admin portal     3001 -> Organization portal      HTTPS + a password, the only published ports
                                 nginx gateway, 7 services with their one-shot <service>-migrate containers, 2 portals, PostgreSQL: private Docker network only
             EBS data disk (40 GB, encrypted, daily snapshots) = Docker's data directory: the databases and the uploaded logos
             SSM Parameter Store  /impex/prod/env/* -> the .env   /edge/* -> the front-door password   /deploy/* -> repository + token   (secrets encrypted with a KMS key)
             Session Manager = the only way in (no SSH, port 22 is closed)
```

`vercel.json` (and `scripts/check_vercel_config.py`, which only checked it) were deleted. `docs/vercel.md` is kept only as history.

## Layout (`infra/terraform`)

| Module | One job |
| :--- | :--- |
| `modules/network` | VPC, public subnet, the Elastic IP, the firewall: **only** the two HTTPS ports are open, to `allowed_cidrs`; outbound is limited to HTTPS, HTTP (OS packages), DNS and e-mail submission (587/465) |
| `modules/security` | a customer-managed **KMS key** (yearly rotation) for the secrets, and the server's IAM role: Session Manager, its **own** parameters (`/impex/<env>/*`) and decrypting them only through SSM; nothing else |
| `modules/config` | SSM parameters, the generated secrets, the front-door password, the `impex-<env>-deploy` command |
| `modules/server` | the EC2 instance (`files/user_data.sh.tpl` first boot, `files/deploy.sh` every deploy), the data disk, the daily snapshots |
| `infra/bootstrap` | run once: the encrypted, versioned S3 bucket and lock table for the Terraform state |

## Security

* **HTTPS and a password in front of both portals.** The edge (`gateway/Caddyfile.aws`, `docker-compose.aws.yml`) is the only thing that is published. It terminates TLS (a certificate from Caddy's local authority: browsers warn once until you trust it or a domain with a real certificate replaces it) and requires **HTTP basic authentication** before any request reaches a portal; the password is never passed on to the portals, which keep their own sign-in. The password is 32 random characters, generated by Terraform and stored encrypted in SSM; on the server only its bcrypt hash exists. Get it with the `get_front_door_password` output. Security headers (`nosniff`, frame and referrer policy) are added and the `Server` header is removed.
* **A closed firewall.** Only 443 and 3001 accept connections; no SSH, no 80, none of the services' ports, PostgreSQL on localhost. Outbound is allow-listed.
* **No standing access.** You get a shell with Session Manager (`aws ssm start-session`), which is authenticated by IAM and logged by AWS. The server's IMDS is v2-only with a hop limit of 1, so a container on the server cannot borrow the server's AWS role.
* **Least privilege.** The server's role can read its own parameters and decrypt them through SSM, nothing else. The account's administrators manage the key; the server cannot.
* **Secrets** are generated once (48 random letters and digits), kept as SecureStrings under the KMS key, written to `/opt/impex/.env` with mode 600, and never put into Terraform variables or the repository. Rotate them in SSM and redeploy.
* **Encrypted at rest**: both server disks and every snapshot; the Terraform state (below) is encrypted and versioned.
* **Protection against accidents**: the data disk cannot be destroyed by Terraform (`prevent_destroy`) and the server has API termination protection.

Not included (decide when it matters): a domain with a real certificate (Caddy or an Application Load Balancer + ACM), AWS WAF, VPC flow logs, CloudTrail/GuardDuty (account-wide services), and a managed database (RDS).

## Configuration lives in SSM

Every parameter under `/impex/<env>/env/` becomes one line of `/opt/impex/.env` at deploy time (the parameter name is the variable name).

| Kind | Parameters | Set by |
| :--- | :--- | :--- |
| plain | `PUBLIC_HOST`, `POSTGRES_USER`, `NEXT_PUBLIC_API_GATEWAY_URL`, `APP_BASE_URL`, `TENANT_PORTAL_URL`, `SUPER_ADMIN_PORTAL_URL` (all `https://<Elastic IP>`), `DEMO_MODE`, `SMTP_PORT`, `SMTP_STARTTLS`, `SMTP_SSL`, `SMTP_FROM_NAME`, `FINANCE_SYNC_*` | Terraform |
| secret (SecureString) | `POSTGRES_PASSWORD`, `AUTH_SECRET_KEY`, `AUTH_INTERNAL_API_KEY`, `ORG_ACTIVATION_API_KEY`, `MODULE_INTERNAL_API_KEY`, `RESERVATION_API_KEY`, `PURGE_API_KEY` | Terraform generates them once; change them in SSM |
| yours | `SMTP_HOST`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_ADDRESS`, `SUPPORT_NOTIFICATION_EMAIL`; `deploy/GITHUB_TOKEN` (only if the repository is private) | **you**, in SSM: they start as `__SET_ME__`, Terraform never overwrites them, and one that is still `__SET_ME__` is left out of the `.env` |
| front door | `edge/BASIC_AUTH_USER`, `edge/BASIC_AUTH_PASSWORD` | Terraform (generated); change in SSM |

```powershell
aws ssm put-parameter --name /impex/prod/env/SMTP_HOST --type String --value smtp.example.com --overwrite
aws ssm put-parameter --name /impex/prod/env/SMTP_PASSWORD --type SecureString --value "the-password" --overwrite --key-id alias/impex-prod-secrets
aws ssm send-command --document-name impex-prod-deploy --instance-ids <instance-id>     # (the `deploy_command` output)
```

Do not put a single quote (`'`) in a value: the `.env` format has no way to escape it.

## First deployment

1. **The AWS account must be fully activated.** A brand-new account answers `You are not subscribed to this service` for EC2 and SSM until sign-up (payment method, phone verification) is finished, which can take up to 24 hours.
2. Use an **IAM user or role, not the root user**: create an administrator IAM user (or IAM Identity Center), sign in to the CLI with it, and delete any root access keys.
3. **Remote state (once).**
   ```powershell
   cd infra\bootstrap; terraform init; terraform apply      # prints a backend "s3" block
   ```
   Paste that block into `infra/terraform/versions.tf` (where the commented one is).
4. **The platform.**
   ```powershell
   cd infra\terraform
   copy terraform.tfvars.example terraform.tfvars            # region, size, allowed_cidrs
   terraform init
   terraform plan -out tfplan
   terraform apply tfplan
   ```
   Without a local Terraform: `docker run --rm -it -v "$PWD:/w" -w /w -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN -e AWS_REGION hashicorp/terraform:1.9 plan` (with `aws login` sessions, export the credentials first: `aws configure export-credentials --format env`).
5. The first boot installs Docker, mounts the data disk, creates a 4 GB swap file, reads the parameters, clones the repository and runs `docker compose up -d --build` (**20-30 minutes** on a t3.small). Follow it:
   ```powershell
   aws ssm start-session --target <instance-id>        # needs the Session Manager plugin
   sudo tail -f /var/log/impex-bootstrap.log /var/log/impex-deploy.log
   ```
6. Open `https://<public_ip>` (Super Admin) and `https://<public_ip>:3001` (Organization portal), accept the certificate warning once, and sign in to the front door with user `impex` and the password from the `get_front_door_password` output.

Each service waits for its one-shot `<service>-migrate` container (see [`database-migrations.md`](database-migrations.md)), so a deploy that adds a migration applies it before the new code starts, and a failed migration stops the update (the script reports it and exits non-zero).

## Deploying later

Push to the branch, then run the deploy command. It pulls, rebuilds, migrates and restarts; it never touches the data disk or the databases. Configuration changes (SSM) are applied the same way. Terraform is only needed to change the infrastructure.

## Create the first Super Admin

A fresh database has no Super Admin. Create one from the server (`aws ssm start-session`), as the verification scripts do (a one-off `docker compose exec auth-service python -c ...` that adds a `super-admin` user). Keep `DEMO_MODE=false` in production.

## Things to know

* **The browser certificate warning** is expected with an IP address and Caddy's own authority. With a domain name, point it at the Elastic IP, set `PUBLIC_HOST` and the URLs in SSM to it, and Caddy can obtain a real certificate (that also needs port 80 open).
* **PostgreSQL runs in a container on the data disk**, protected by daily snapshots (crash-consistent, which PostgreSQL recovers from). A managed database (RDS: one instance, the same seven databases) is the better home once there are real customers.
* **Cost** (us-east-1, on demand, roughly): t3.small about 15 USD a month, 70 GB of gp3 about 6 USD, the Elastic IP about 4 USD, the KMS key 1 USD, snapshots a few USD: about **28 USD a month**.
* **t3.small is the smallest size that works, not a comfortable one.** 2 GB of memory: the running stack fits, the server has a 4 GB swap file and builds one image at a time, so the first deploy is slow and a busy moment can be sluggish. If so, set `instance_type = "t3.medium"` (about 30 USD a month) and run `terraform apply -replace=module.server.aws_instance.this`: the data disk moves with it.
* **Replacing or destroying.** A new server mounts the same data disk and finds the databases where they were. To destroy everything, remove `prevent_destroy` on purpose, take a snapshot first, switch off `termination_protection`, then `terraform destroy`.
